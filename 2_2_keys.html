Keys

five ways to make sure no two rows are ever the same

§1 Why keys exist

There must be some way to uniquely identify the tuples in a relation — no two tuples in a relation are allowed to have exactly the same values across every column. Keys are the mechanism that guarantees this.

Super Key Candidate Key Primary Key Unique Key Foreign Key

§2 The five key types

1 · Super Key

Any attribute, or set of attributes, that uniquely identifies a single tuple. A table can have many super keys.

Student{roll_no, name, address, city, pin_code, gender}
Super keys: {roll_no}, {name, city}, {name, city, address}

2 · Candidate Key

A minimal super key — remove any attribute and it stops being a super key. Candidate keys are chosen from among the super keys, with no redundant attribute.

Student{roll_no, enrol_no, stud_name, percent, address, phone_no, email_id}
Candidate keys: {roll_no}, {enrol_no}, {stud_name, address}

§3 Foreign Key

A foreign key creates a link between two tables — it references the primary key of another table. If relation schema R1 includes among its attributes the primary key of another schema R2, that attribute is a foreign key in R1 referencing R2.

the Employee table's DeptID (foreign key) must match a DeptID already in Department (its primary key)

  • Department is the referenced relation (a.k.a. parent / master table)
  • Employee is the referencing relation (a.k.a. child / detail table)
  • The foreign key column can only hold values that actually exist in the referenced primary key — this rule is called referential integrity
